# 指标口径字典

> **为什么口径必须写下来**：同一个"活跃用户"两个人算出两个数，是数据团队最常见的内耗。
> 口径写在这里、也写在对应 SQL 的注释里（**口径必须和代码在一起**，
> 否则改代码的人不会同步改外部文档）。
>
> 每一条包含四部分：**定义 / 公式 / 边界条件 / 已知局限**。

---

## 一、口径总表

| 指标 | 字段 | 定义 | 公式 |
|---|---|---|---|
| DAU | `dau` | 当日产生过任意行为事件的去重用户数 | `count(distinct user_id)` |
| 新增用户 | `new_users` | 当日首次出现行为的用户数 | `首次出现日 = 当日 的用户数` |
| PV | `pv` | 当日页面访问次数 | `count(event='pv')` |
| 浏览用户 | `visit_users` | 当日有 pv 的去重用户数 | `count(distinct user_id where pv>0)` |
| 订单数 | `order_cnt` | 当日有效且已支付的订单数 | `sum(order_cnt)`（按 order_id 去重） |
| GMV | `gmv` | 当日有效且已支付的金额合计 | `sum(amount)`，**净 GMV** |
| 支付用户 | `pay_users` | 当日有效且已支付订单的去重用户数 | `count(distinct user_id)` |
| 客单价 | `aov` | 平均每单金额 | `gmv / order_cnt` |
| 支付转化率 | `pay_conversion` | 支付用户占浏览用户比例 | `pay_users / visit_users` |
| 人均收入 | `dau_arpu` | 每个活跃用户贡献的 GMV | `gmv / dau` |
| Top1 商品占比 | `top1_sku_share` | 最大单商品 GMV 占当日比例 | `max(sku_gmv) / sum(sku_gmv)` |

## 二、逐条口径说明

### GMV（最容易被问、也最容易算错）

- **定义**：当日**有效且已支付**订单的金额合计。
- **公式**：`sum(amount)` where `is_valid and is_paid`。
- **边界条件**：
  - **不含退款单**：`order_status='refunded'` 的订单不计入（源数据把它标成退款，不是删除）；
  - **不含重复订单**：按 `order_id` 先去重，一单只算一次；
  - **不含无效金额**：金额为空、为负、`user_id` 为空的订单在 DWD 被判为无效，不入指标；
  - **不含运费/优惠**：本项目源数据只有成交金额，没有拆出这些科目。
- **已知局限**：
  - 与财务口径不同。财务口径通常按**结算时间**（而非下单时间）认收入，且要扣除平台补贴与佣金；
  - 本项目按**下单时间**归日，所以跨月下单/退款会与财务对不上；
  - **面试常问**："你们的 GMV 和财务为什么不一样？" ——答案就是上面这两条，能说清就是加分。

### 支付转化率

- **定义**：当日支付用户数 ÷ 当日浏览用户数。
- **公式**：`pay_users / visit_users`（**人数口径**，不是次数口径）。
- **边界条件**：
  - 分母是**浏览用户**（有 pv 的人），不是 DAU——可能有只加购不浏览的用户；
  - 分子来自**订单表**（真实支付），分母来自**行为日志**；
  - 分母为 0 时取 0（不产生除零）。
- **已知局限**：
  - **这是"当日转化"，不是"用户级漏斗转化"**。用户今天浏览、明天下单，不会被算进今天的转化；
  - 两个口径都有用途：当日转化看的是"当天流量的即时变现效率"，
    用户级漏斗看的是"一个人从看到买的路径"。**混用会得出错误结论。**

### 转化漏斗（`ads_funnel_1d`）

- **定义**：浏览 → 加购 → 下单，各阶段的去重用户数与相对上一阶段的转化率。
- **边界条件**：
  - 浏览 = 当日产生过任意行为事件的用户；加购 = 当日有 `cart` 事件的用户；
    下单 = 当日有 `buy` 事件的用户；
  - **漏斗的"下单"用的是行为日志的 `buy` 事件，不是订单表**。
    原因：漏斗要的是"用户站内行为序列"，用行为日志才自洽
    （订单表的支付可能发生在浏览的第二天，混进来会让"同日漏斗"失真）。
- **已知局限**：
  - ⚠️ **漏斗的"下单"与 `ads_daily_metrics.pay_users` 不是一个口径，不可交叉相加或互相验证**；
  - 只统计"当日发生过该行为"的人数，不保证行为顺序（不校验 cart 一定发生在 buy 之前）。

### DAU 与新增用户

- **定义**：DAU＝当日有任意行为事件的去重用户；新增＝当日首次出现行为的用户。
- **边界条件**：
  - "首次"是**相对本统计窗口**的首次，不是注册以来首次。
    窗口外还有活动的用户，在窗口第一天会被算成"新增"——这是滑动窗口的固有性质；
  - 事件日期必须落在窗口内（`dwd_page_log` 已按窗口过滤）。
- **已知局限**：
  - 若需要"注册以来首次"，应当关联 `dim_user.reg_date`，本项目为保持口径简单没有这么做；
  - 没有区分自然新增与召回。

### Top1 商品占比

- **定义**：当日 GMV 最大的单个商品占当日 GMV 的比例。
- **用途**：**量化数据分布是否倾斜**。实测热销 SKU 占订单量的 40%，
  这个指标是用来在指标层"看见"倾斜的——不然倾斜只存在于代码和性能里。

## 三、口径变更记录

| 日期 | 变更 | 原因 |
|---|---|---|
| 2026-10-05 | DWS 层金额聚合加 `ROUND(...,2)` | `DOUBLE` 累加依赖顺序，导致重跑结果末位不一致（`8660.22` vs `8660.220000000001`），"重跑逐行一致"这条性质无法验证 |
| 2026-10-05 | `not_null_rate` 阈值 0.999 → 0.995 | 注入的空值约占万分之十一，原阈值会让每次跑批都被自己的测试数据阻断；阈值应按"业务能容忍多少"定，不是拍脑袋 |

> 记录口径变更和记录代码变更同样重要：**指标数字变了，第一件事是查口径有没有改过。**
