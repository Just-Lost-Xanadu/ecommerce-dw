# 扩展方向评估（暂不实施）

> 主线（五层数仓 + 质量门禁 + 幂等调度）已经完整。
> 2026-10-20 已补可选的 Airflow 调度层（`dags/` + `docs/airflow.md`），只做定时、重试、补数、告警，
> 不改变主线 runner。下面列出其余可选方向，按投入产出比排序；**同时只做一个**，
> 避免摊薄主线深度。

---

## 1. 拉链表（SCD2）—— 首选，成本低、设计价值高

**做什么**：把 `dim_user` 改成 `dim_user_zip`，支持历史状态回溯。

**为什么优先**：
- 代码量小（约 30 行 SQL），但能覆盖一个完整的数仓设计问题；
- 能解决一个真实问题：用户改过城市/手机号之后，"上个月的报表按当时的信息算"怎么做。

**核心结构**：

| 字段 | 含义 |
|---|---|
| `user_id` | 业务键 |
| `start_date` / `end_date` | 这条记录的有效区间 |
| `is_current` | 是否当前有效 |

**关键实现点**：
1. **开链与闭链**：新记录插入时 `end_date` 取一个极大值（如 `9999-12-31`），
   变更时把旧记录的 `end_date` 改成变更日**前一天**，再插入新记录；
2. **去重要用"变更检测"**：只有属性真的变了才开新链，否则每天都会产生一条无意义的历史；
3. **查询要加时间条件**：`WHERE start_date <= 某日 AND end_date >= 某日`——
   这是拉链表最容易被写错的地方（漏了就会一行变多行）；
4. **幂等**：重跑同一天的拉链，结果必须一致（建议按"分区重建 + 只处理变更"来做）。

**怎么验证**：造一批"用户改城市"的数据，跑两遍，验证
① 历史时刻查询能查到旧值；② 重跑不产生重复链。

## 2. 实时指标（Kafka + Flink）—— 暂缓

**做什么**：算一个实时 GMV，写回 MySQL/看板。

**为什么暂缓**：
- Flink 的组件门槛最高（事件时间、水位线、状态、Exactly-once）；
- 它会**直接吃掉排期**：本地起 Kafka + Flink 的环境成本，与主线五层数仓相当。

**如果一定要做，最小形态是**：
Kafka 造一个订单事件流 → Flink 做 5 分钟滚动窗口求和 → 写入一张结果表。
**重点不是跑通，而是能讲清**：事件时间 vs 处理时间、乱序与水印、
状态后端、以及"至少一次"和"精确一次"的差别。

---

## 3. 调度可视化看板 —— 锦上添花

**做什么**：把 `run_steps` 与 `quality_results` 渲染成页面：任务成功率、耗时趋势、质量趋势。

**为什么价值中等**：数据已经落库（这是重点），可视化只是展示层；好处是能直接打开看，
比讲"我记录了 trace"更直观。

**成本**：低（复用现有 HTML 渲染代码）。

---

## 4. 不推荐的方向（说明理由，避免走弯路）

| 方向 | 理由 |
|---|---|
| Hadoop 集群运维 | 本地演示不需要；只搭环境不产生可验证的数据结论 |
| Scala | 与当前 Python/SQL 主线重复，收益低 |
| 为凑关键词塞一个玩具级"多 Agent 协作" | 主线定位是"单 Agent + 工具层"，加假的反而拉低可信度 |
| 硬塞消息队列 | 单副本单进程本来不需要 MQ；应先讲清"什么规模下才需要" |
| 再扩语料/再扩指标 | 边际收益极低。把「已知不足」写扎实比多堆三个指标有用 |
