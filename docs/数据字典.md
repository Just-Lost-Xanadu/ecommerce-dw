# 数据字典

> 每张表的字段含义、来源、以及**为什么这么设计**。
> 字段命名约定：`_` 开头的是运行元数据（批次、加载时间），业务字段不加前缀。

---

## ODS 层（原始落地）

### `ods_order_info`

订单原始数据。**不做任何业务清洗**——脏行也保留，它们是质量分析的证据。

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `order_id` | VARCHAR | 订单系统 | 订单号；**源数据中可能存在重复** |
| `user_id` | VARCHAR | 订单系统 | 下单用户；**可能为空**（源数据脏） |
| `sku_id` | VARCHAR | 订单系统 | 商品；**可能不在商品维表中**（孤儿） |
| `quantity` | INTEGER | 订单系统 | 件数 |
| `unit_price` | DOUBLE | 订单系统 | 成交单价（≠ 商品维表的标准价） |
| `amount` | DOUBLE | 订单系统 | 成交金额；**可能为空或为负** |
| `order_date` | DATE | 订单系统 | 下单日期；**可能是未来日期** |
| `order_status` | VARCHAR | 订单系统 | `paid` / `refunded` |
| `channel` | VARCHAR | 订单系统 | 下单渠道 `app` / `h5` / `mini` |
| `_load_time` | TIMESTAMP | 入仓时间 | 由加载语句写入 |
| `_source_file` | VARCHAR | 入仓 | 来源文件名（血缘的最小实现） |
| `_batch_id` | VARCHAR | 入仓 | 批次号 |
| `dt` | DATE | 入仓 | **分区键**，等于 `order_date` |

### `ods_user_log`

行为日志原始数据。同样不过滤窗口外的迟到数据——那是 DWD 的职责。

| 字段 | 类型 | 说明 |
|---|---|---|
| `log_id` | VARCHAR | 日志主键 |
| `user_id` | VARCHAR | 用户；**可能为空** |
| `sku_id` | VARCHAR | 关联商品 |
| `event` | VARCHAR | `pv` / `cart` / `fav` / `buy` |
| `log_date` | DATE | 事件日期 |
| `stay_seconds` | INTEGER | 停留时长 |
| `_load_time` / `_source_file` / `_batch_id` / `dt` | — | 同订单表 |

## DIM 层（维度）

### `dim_sku`

| 字段 | 说明 |
|---|---|
| `sku_id` | 商品主键 |
| `sku_name` / `category` / `brand` | 名称、一级类目、品牌 |
| `price` | **标准价**（≠ 订单里的成交价。分析成交额用订单 `amount`，分析品类结构才用维度价——混用会造成口径不一致） |
| `_batch_id` | 批次 |

### `dim_user`

| 字段 | 说明 |
|---|---|
| `user_id` | 用户主键 |
| `phone` / `city` / `age` / `reg_date` | 属性 |
| `is_conflict` | **源数据里同一 user_id 存在多条冲突记录时为 true**。处理方式是保留一行并**标记**，而不是随便取一条——随便取会让"这个用户是哪个手机号"变成不确定的 |
| `_batch_id` | 批次 |

### `dim_date`

| 字段 | 说明 |
|---|---|
| `date_key` | 日期主键 |
| `year` / `month` / `day` / `weekday` / `weekday_cn` / `is_weekend` | 日期属性 |

> **为什么需要日期维度**：如果某天一个订单都没有，直接从事实表 `group by` 出来的指标表会**缺这一天**，
> 报表出现断点，看起来像"数据丢了"。有了日期维度才能 LEFT JOIN 出"这天确实没有数据（值为 0）"。
> 这是"报表为什么断了一天"的标准答案。

## DWD 层（明细）

### `dwd_order_detail`（事实表）

**粒度：一行 = 一个订单里的一个商品。**
（不是"一行一订单"——因为要按品类/商品分析，订单粒度做不到；粒度必须在建表时定死。）

| 字段 | 说明 |
|---|---|
| `order_id` / `user_id` / `sku_id` | 业务键（已去重） |
| `sku_name` | 冗余商品名，避免报表每次回联维表；**孤儿商品为 NULL，是可见的而不是消失** |
| `quantity` / `unit_price` / `amount` | 度量 |
| `order_date` / `order_status` / `channel` | 属性 |
| `is_paid` | 是否已支付（退款单为 false） |
| `is_valid` | **是否通过有效性校验** |
| `reject_reason` | 无效原因；有效行为 NULL。取值：`user_id_null` / `amount_null` / `amount_not_positive` / `date_in_future` |
| `_batch_id` / `dt` | 元数据与分区 |

> **为什么标记而不删除**：直接删掉的话，报表与业务库对不上账时你只能猜"是不是清洗洗掉了"；
> 标记之后可以直接 `SELECT reject_reason, count(*) ... GROUP BY 1` 看剔了多少、为什么剔。

### `dwd_order_reject_audit`

剔除审计表：按 `dt` 统计每类剔除原因的行数，供质量报告与对账使用。

### `dwd_page_log`

清洗后的行为明细。相较 ODS：
① 丢掉 `user_id` 为空的行为（无法归属到人，做不了 UV / 漏斗）；
② 丢掉超出统计窗口的迟到数据（**不是错，是来晚了**——在 T+1 批处理里属于上一批该处理的范围，
由源边界规则单独监控，而不是静默丢弃）。

## DWS 层（轻度汇总）

### `dws_traffic_user_1d`

用户 × 天的流量汇总：`pv` / `cart_cnt` / `fav_cnt` / `buy_cnt` / `stay_seconds` / `event_cnt`。

### `dws_trade_user_1d`

用户 × 天的交易汇总：`order_cnt` / `sku_cnt` / `pay_amount`。

> `pay_amount` 用 `ROUND(sum(amount), 2)` 收敛到分——**明细保真、汇总定精度**，
> 这样重跑结果才能逐行一致。

## ADS 层（指标）

### `ads_daily_metrics`

每日核心指标，一行一天。字段与口径详见 [`指标口径.md`](指标口径.md)。

### `ads_gmv_category_1d`

按 天 × 一级类目 的 GMV、订单数、商品件数、用户数。

> **孤儿商品在这里归入「未知类目」**。如果 DWD 与 `dim_sku` 用 INNER JOIN，
> 这些订单会**静默消失**——GMV 少了却看不出原因。
> 归到一个显式的「未知类目」后，它变成**可见**的，质量规则也能单独监控它的占比。

### `ads_funnel_1d`

按 天 × 阶段（view / cart / buy）的人数与相对上一阶段的转化率。
**注意"下单"是行为口径，与 `ads_daily_metrics.pay_users` 不是同一个口径。**

## 运行元数据（SQLite：`data/meta.sqlite`）

### `run_steps`

每次跑批每一步的记录。

| 字段 | 说明 |
|---|---|
| `run_id` / `step` | 运行号 / 步骤名（ods、dim、dwd、quality、dws、ads） |
| `status` | `ok` / `failed` / `blocked` |
| `started_at` / `duration_ms` | 时间与耗时 |
| `in_rows` / `out_rows` / `dropped_rows` | 输入、输出、丢弃行数 |
| `message` | 摘要或失败原因 |

### `quality_results`

每条规则每次运行的结果，**保留历史**——这样才能看出"质量在退化"，而不只是"这次过没过"。

| 字段 | 说明 |
|---|---|
| `run_id` / `layer` / `rule` / `layer_table` | 定位 |
| `passed` / `actual` / `threshold` / `blocking` | 判定 |
| `affected_rows` | 影响行数（**每条规则只报实际触发的量**） |
| `detail` | 这条规则在检查什么 |
| `created_at` | 便于按时间看趋势 |
